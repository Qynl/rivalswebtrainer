# Multiplayer burst/stall handling

This pass targets additional sources of stutter in the static-site PeerJS path. It does not change movement tuning, damage, inventory, projectile authority, aim or graphics quality. No backend setup is added.

## Changes

- **Disposable combat effects no longer occupy reliable gameplay control.** New guests advertise `effectsLane: 1`. With a working realtime channel, the host separates only bullet traces and wall impacts from reliable events. Damage feedback, kills, launches/impulses, round events and other controls remain reliable. Each cosmetic batch is at most 1,000 UTF-8 bytes / 12 events; fresher effects win when a batch is too large. A per-peer 1,500-byte burst / 12,000-byte-per-second token budget limits cosmetic traffic, and it yields when the outgoing queue exceeds 1 KiB. Congested/failed cosmetic sends are discarded, not retransmitted through reliable control.
- **Independent event deduplication.** The cosmetic lane uses a bounded 256-ID set, not the critical event high-water mark. Out-of-order visual packets cannot suppress a later-arriving hit, kill, self-launch or forfeit. Reliable fallback duplicates are deduplicated too. Incoming effects reject foreign matches, oversized batches, non-cosmetic event types and malformed/non-finite positions.
- **Monotonic opponent playback.** Adaptive clock-offset and jitter estimates previously moved the sampled timestamp directly, including backward after arrival spikes. Playback now advances continuously with bounded ±15% rate adjustment; it never rewinds just because the delay estimate changes. Extrapolation remains capped at 50 ms and interpolation at the existing adaptive 55–120 ms. A long suspended frame may resynchronize forward, not backward; new rounds reset the clock.
- **Newest-state inbox.** Incoming PeerJS snapshots queued within one event-loop turn collapse to the newest state. Critical messages flush pending state first. Closing the transport or changing connection generation prevents queued delivery. This removes redundant reconciliation/model/projectile updates after bursts without waiting for a rendered frame, so paused HUD/countdown updates still work.
- **No catch-up input bursts.** Fixed simulation ticks mark held input as due; presentation sends the freshest held state at most once per frame, capped at 60 Hz. Discrete actions and WASD transitions still send immediately. Physics remains 120 Hz. A 200 ms catch-up no longer submits twelve obsolete intermediate movement packets.
- **Multi-shot confirmations.** A delayed/coalesced snapshot can confirm multiple shots. The authoritative shot-stat delta now retires all corresponding pending local presentations, including across weapon switches, rather than leaving phantom pending shots that suppress further firing feedback. Non-shot statistic changes update the baseline without retiring a prediction. This only affects presentation: it does not spend or grant ammo, create projectiles, confirm hits, or deal damage.

The realtime sender drops replaceable state when its buffered amount exceeds 2 KiB (previously 8 KiB). These are high-water thresholds, not absolute packet-size limits; snapshot/projectile frames can themselves exceed them. Unsupported/closed state channels, guests without the optional capability, and explicit reliable recovery retain the compatible reliable event path. Reliable control and disposable data still share the underlying WebRTC association/link: this is traffic prioritization, not a guarantee of bandwidth or independent congestion control.

## Reproduced regressions

The new tests were replayed against the previously shipped `8d2a8c4` protocol/session methods, resolving their dependencies to the same source tree. This isolates these algorithms; it is not a complete historical-build FPS benchmark.

| Controlled case                                                                                                     | Previous methods                                                          | Updated methods                                                           |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 12-second, 144 Hz remote playout; 30 Hz state, 40 ms base one-way delay, variable jitter, 20% loss and 180 ms holds | 15 backward steps; worst −0.0348 units; largest forward step 0.5333 units | 0 backward steps; maximum step 0.0639 units at speed 8                    |
| One snapshot acknowledges six predicted shots                                                                       | 5 phantom pending shots remain                                            | 0 remain; no duplicate presentation or ammo mutation                      |
| 200 ms fixed-step catch-up                                                                                          | 12 intermediate held-input packets                                        | 1 freshest held-input packet at presentation; jump/action still immediate |

`tests/realtime-lag.test.js` adds 20 unit regressions covering these cases, critical/cosmetic ordering, congestion budgets, UTF-8 sizing, malformed packets, mixed-version/closed-lane fallback, generation cancellation, 30/60/144 Hz delivery and round/stall resets. The complete unit suite passed **522/522**; production build passed.

The clean production-browser sweep passed **12/12 scenarios in 4.5 minutes**, covering static-only invitations, readiness/loadouts, leave/rejoin and host-close behavior; paused countdown/HUD, loss/reordering/reliable recovery; six-client 3v3 firing; adverse host/guest movement; optional WebSocket authority/collision parity; calmer movement controls; all 17 firearms/reload rendering and unchanged aim; and a disconnected production reload/range session.

In the six-client case, each authority-controlled player fired **17 real shots**. Cosmetic traffic was additionally delayed **60–100 ms**, with every fourth cosmetic packet dropped. Each guest received **60 new snapshots** during the roughly two-second combat sample and **12–13 effect batches**; **zero trace/impact events used reliable combat-event packets**. Explicit reliable ping/control round trips were **2 ms locally**. This is local control-path verification, not an Internet ping claim.

With the existing approximately 80 ms one-way delayed/lossy input-and-state trace and 260 ms reliable input-action delay, host travel was **25.2505 units**, guest **25.0353** (about **0.85% less**). Both had **zero backward movement steps** and **0–8 ms local input response**. Maximum horizontal correction was **0.127 / 0.222 units**. These figures are from a frozen-render transport/worker harness, not a six-device GPU/FPS benchmark.

The first browser sweep caught an `Illegal invocation` from storing a native browser timer cancellation function as an inbox method. A lexical wrapper fixed the browser binding; a strict-context unit regression was added. All twelve scenarios were rerun successfully on the corrected build. The RTC suite uses static production assets with `/api` deliberately unavailable and test-only local signaling. Its six independent clients use real channels/worker authority and real firing, but not six GPU renderers. Delays/loss are injected by the test harness, not an Internet-wide benchmark. Public PeerJS discovery/NAT/relay performance and republishing the user's external site remain unverified.

## Using the update

Both players should refresh the updated frontend and create a **new lobby**. A Git push does not prove that an independently published site has deployed these assets. Keep the host tab active. Slow hardware, background-tab throttling, a poor host uplink, high Internet RTT or a relay can still cause lag; no backend-free transport can guarantee zero latency.
